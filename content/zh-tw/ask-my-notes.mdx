## 背景

這個網站的右下角有一本可以對話的筆記本。它是整個作品集裡唯一能「用」、而不只是「讀」的部分；它之所以存在，是因為我現在想應徵的許多職位都要求 LLM 整合經驗，而最誠實的展示方式，就是真的做一個上線。

作品集聊天機器人最難的地方不是讓它說話，而是讓它閉嘴。問一個模型關於某個它從沒聽過的人，它會生出一份自信、合理、但完全捏造的履歷，而每一個捏造的細節，都可能被招募人員在面試時拿來問我。這個網站其餘的部分都在主張：大聲的失敗勝過看似合理的錯誤答案。一個會亂猜的機器人，等於在頁面上最顯眼的地方自打嘴巴。

所以設計目標很窄：它只能說出我筆記裡寫著的東西；不知道的時候，必須用一種我可以計數的方式說出來。

## 我做了什麼

這個助理叫 PATS，是 Portfolio Assistant & Talent Scout 的縮寫。這個名字只說明它在做什麼，於是真正有意思的主張，就留給讀者可以親自驗證的地方：設定面板。PATS 有三個轉盤，其中一個轉不動。誠實度固定在 100，和旁邊兩個一樣一格一格畫出來，但每一格都沒有作用。招募人員可以伸手去調、試著把它調低，然後發現它是焊死的。

這是把這個專案的規格做成一個控制項，而不是一句話；它借用的那個梗正好點出重點。在《星際效應》（Interstellar）裡，TARS 的誠實度設定在 90%，Cooper 問起時得到的回答是：對有情緒的生物來說，絕對的誠實並不總是最圓融、也不是最安全的溝通方式。

這個理由在這裡不成立。TARS 是在深太空裡照顧一組太空人的士氣；PATS 回答的是關於一份履歷的問題，它說的話沒有任何情緒上的分量，所以 TARS 保留的那一成換不到任何圓融，只會犧牲準確。它跑在 100，而且這是唯一不會動的設定。以下的一切，都是讓這件事成立的機制。

五個 markdown 檔（個人資料、專案、工作方式、興趣、常見問題）會在模組載入時串接成一段 system prompt，目前長度是 10,870 個 tokens。機器人能說出的每一個事實，都在這些檔案裡。只要有任何一個檔案遺失或是空的，建置就會失敗，而不是部署一個知識有破洞的機器人。

當答案不在筆記裡，機器人會用一句固定的句子結束回覆，一字不差：

> That's not in my notes — you can ask Suyu directly at suyu0229@gmail.com.

這句話不只是禮貌，它就是量測工具。一個私人的管理頁面會隨選分析記錄下來的對話，靠比對這個一字不差的字串找出內容缺口，所以機器人答不出來的每個問題，都會變成「我該補寫哪些筆記」清單上的一個具體項目。機器人的無知，就是這個產品的功能。

訪客這一端是一個延遲載入的 widget。首次載入的 bundle 裡只有入口按鈕；面板和它的串流邏輯，要到第一次打開時才會送達。回覆透過分塊的純文字回應，一個 token 一個 token 地串流出來。

## 關鍵決策與取捨

**一句固定的拒答句，而不是逐則訊息標記。** 另一個做法是每則訊息再多呼叫一次分類，標記為已回答或未回答。這會讓熱路徑上的成本和延遲加倍，只為了得到字串比對早就告訴我的事。每輪只呼叫一次模型，缺口偵測順帶免費完成。代價是這句話從此凍結：只要改動它的措辭，所有已記錄的缺口都會悄悄失去對應。

**準確優先於流暢。** system prompt 禁止機器人在筆記之外補充、估計或加油添醋，而且是逐字引用拒答句，而不是描述它。這刻意讓機器人在對話上變差：問它一個和它已知事實相鄰的問題，它不會替你補上中間的空白。這正是我要的取捨。回答得太少的機器人還能補救；回答得太多的，會在招募人員面前替我亂說話。

**system prompt 逐位元組凍結。** prompt caching 只有在快取的前綴每次都完全相同時才有用，所以任何動態內容都不能碰它。沒有時間戳記，也沒有訪客的情境。你在某個案例頁打開聊天時，機器人知道你正在讀哪一篇，但這個情境是放進 *user* 回合裡的。實測結果：每次重複的請求，完整的 10,870 個 tokens 都從快取讀取，價格大約是輸入價格的十分之一。

**官方 SDK，而不是包裝層。** Vercel 的 AI SDK 能讓我更快起步，但串流、快取和拒答處理正是值得展示的部分，而包裝層剛好把這些藏起來。直接使用 SDK，也代表要處理那些包裝層會替你掩蓋的事。Opus 5 可能回傳 200，同時帶著 `stop_reason: "refusal"`，所以程式在讀取任何內容之前會先檢查 stop reason，並改用拒答句，而不是串流出一個說到一半的答案。

**Postgres，而不是文件資料庫。** 聊天記錄在你開始查詢之前，看起來都像文件。我需要的是 session 對應到訊息，而我對它們的每一個問題（最常被問什麼、哪些回合觸發了拒答句）都是一個 group-by。關聯式 schema 用 SQL 回答這些問題，而不是靠應用程式碼。支持文件資料庫的資料量論點在這裡也從來不成立：在規模變成問題之前，每日上限的保險絲早就先把寫入切斷了。

**在 Postgres 裡做流量限制，而不是另加一個服務。** 兩個有索引的計數查詢（每個雜湊過的 IP 每五分鐘二十次請求，以及全站每天三百則助理訊息的上限），重複利用原本就在的資料庫，而不是為了兩個計數器另外加一個佇列或 KV 儲存。每日上限是程式裡的常數，不是環境變數，所以要提高我自己的花費上限，得提交一個 commit。雜湊也不是附帶的：流量限制需要認得重複造訪的訪客，而不需要知道他們是誰，所以寫進資料庫的永遠只有位址的 HMAC，而且它不作任何其他用途。

## 出過的錯

流量限制器上線時，失效時會預設*放行*，而我差點沒發現。

每個 IP 的檢查會計算最近的請求數，再和上限比較。寫得很「防禦性」，看起來像這樣：

```ts
if ((result.count ?? 0) >= RATE_LIMIT_REQUESTS) { /* refuse */ }
```

PostgREST 對一張它找不到的資料表做 `HEAD` 計數時，回傳的是**沒有錯誤，加上一個 null 計數**。於是 `null ?? 0` 變成零，零低於上限，每個請求都暢行無阻。花費保險絲偏偏在它存在的理由，也就是資料庫連不上的情況下，被悄悄停用了。

它之所以浮現，只是因為我在套用 schema 之前就先跑了驗收測試，所以那些資料表是真的不存在。如果我先套用 schema，這個檢查會通過我寫的每一個測試，然後以失效的狀態進到正式環境。現在，缺少計數會被當成錯誤，而不是零。

同樣的 null 計數行為，早就騙過我的*驗證*腳本，讓它回報資料表存在、但其實並不存在。這是一次假通過，而那個檢查唯一的工作就是抓出這種事。兩個 bug 來自同一個錯誤的假設，這正好說明為什麼要測試失敗的路徑，而不是只測順利的那一條。

## 成果

這個機器人能準確回答我的背景、四篇案例和求職狀態。它會把離題的問題導回來而不回答它們，在 prompt injection 的嘗試下守住範圍，並用一句簡短的說明婉拒有界線的話題，例如薪資、家庭和移民細節，而不是用拒答句，所以這些永遠不會汙染內容缺口清單。

在一個刻意問到最大的問題上，它用了 1,024 個輸出 token 預算中的 591 個。這一直維持到簡潔度轉盤上線；它較長的設定開始碰到上限，所以預算加倍到 2,048，每日上限也從五百則助理訊息降到三百則來支應。最壞的情況大致維持在原本的位置。

這個 widget 讓首頁的 Lighthouse 維持在效能 96、無障礙與最佳做法 100，累積版面位移為零。

驗證時發現了兩個無障礙缺陷，都是我的錯。入口按鈕帶著一個不包含它自身可見文字的 `aria-label`，這違反 WCAG 的 Label in Name 規則：使用語音控制的人，沒辦法靠說出他們看到的字來啟動它。另外，關閉時焦點從來沒有回到按鈕上，因為面板打開時按鈕被卸載了，所以它想聚焦的 ref 是 null。這兩個問題光看頁面都看不出來。

誠實的限制：這個機器人永遠只會和它背後的筆記一樣好，在我補上它找到的缺口之前，它會一直碰到拒答句。這是設計好的循環，而不是缺陷，但這也代表有意思的工作還在持續，而不是已經完成。
