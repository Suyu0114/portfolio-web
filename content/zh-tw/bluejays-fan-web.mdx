## 背景

我搬到多倫多後，想要有一個地方能真正*讀懂*藍鳥隊的球季：不是一堵數字牆，而是好奇的球迷會在轉播上認出來的那些圖表：打者把球打到哪裡、投手在好球帶的哪裡活動、一名球員的價值如何拆解。多數公開工具不是預設你已經懂棒球統計學，就是把好的資料藏在會員制後面。

所以我從頭到尾做了一個：一條每晚抓取 Statcast 和 MLB 資料的 Python 管線、一個儲存資料的 Postgres 資料庫，以及一個用手刻 D3 圖表呈現資料的 Next.js 前端。以英文為主，並提供可選的繁體中文切換給家鄉的家人；導覽和內文會翻譯，但球員名字和棒球術語（`OPS`、`wRC+`、`Statcast`）刻意維持英文，因為這裡的人實際上就是這樣討論棒球的。

## 關鍵決策與取捨

**ETL 放在應用程式外面。** pybaseball 對 serverless 請求來說太重了，所以我從不在請求時抓資料。一個 GitHub Actions 排程執行 Python 管線、寫進 Supabase，再呼叫 `/api/revalidate` 端點，讓 Next.js 的 ISR 快取在幾秒內失效。另一個做法（在 Vercel function 裡抓資料）會造成緩慢的冷啟動請求和逾時。代價是網站在隔夜更新，而不是即時；對一個看昨天比賽的球迷來說，這是對的取捨。

**球季數據誠實面對它的來源。** FanGraphs 是 WAR 組成、wRC+ 這類數據的唯一來源：它沒有 API，而爬蟲現在會收到 HTTP 403。與其違反他們的條款去爬，我用自己的會員把數字匯出成 CSV，放進一個被 gitignore 的資料夾，檔案缺少時以警告而不是當機的方式載入。球員名單的列舉（「那一年有誰替藍鳥隊出賽」）則改用 MLB Stats API 的全球季端點。自己做的 Savant 圖表（落點圖、熱區圖、守備圖）才是公開網站實際上線的部分；有授權限制的數字只作為私人輸入。

**本壘板對齊標記，因為資料悄悄變了。** 2026 年，Statcast 把 `plate_x`/`plate_z` 的基準從本壘板前緣移到本壘板中央。把兩個球季的投球疊在一起，會讓好球帶悄悄錯位一到三英寸。我在匯入時把每個事件標記為 `front` 或 `middle`，並讓熱區圖只限定一種對齊方式，所以圖表要嘛正確、要嘛是空的，絕不會微妙地出錯。大聲失敗，勝過一張看起來合理的熱區圖。

**把延遲抵達的修正當成正式情況處理。** Statcast 會在比賽後追溯重新分類投球，所以一次性的回補資料會慢慢過時。每晚的排程會對當季重新抓取一個滾動的七天區間，並以複合鍵做 upsert，而已結束的歷史球季則保持凍結。小地方的正確性也受到同樣重視：投球局數是從儲存的出局數重新計算，而不是相信 Statcast 的 `5.2` 小數，它其實代表「5 又 ⅔」，會讓天真的算術出錯。

**在管線裡預先彙總，讓讀取路徑保持輕薄。** 球季數據在 ETL 裡只計算一次，依球員與球季儲存；頁面從不在請求時處理數千筆 Statcast 資料。D3 元件接收的是純 JSON，而不是資料庫 client，所以它們能保持與框架無關、容易測試。因為這個 Supabase 專案和其他工作共用，每張資料表都以 `web_` 前綴作為命名空間，這個小小的紀律避免了和一張原本就存在的 `players` 資料表衝突。

## 成果

三個球季（2024 到 2026，包含 2025 年的季後賽）已為每一位 40 人名單上的藍鳥隊球員回補完畢，而每晚的排程讓當季資料保持最新。落點圖、投球熱區圖、守備圖和打者深入分析，全都以英文和繁體中文上線。WAR 拆解會在頁面上把它的六個得分價值組成加總回 RAR。

這個專案後來也長出了完整的投手面向：一張球種組合表，列出每種球種的使用率、球速、轉速、揮空率和擊中球的預期 wOBA；一張水平與垂直位移圖；以及一條滾動的球速趨勢。守備使用 Statcast 的守備得分價值，而不是一個需要付費資料的指標：這是整個專案反覆出現的主題，資料來源的選擇，和建立在它上面的那張圖表一樣，都是設計決策。

這個專案其實是兩種專業的交會：一條拒絕取近似值、大聲失敗的資料管線，以及一個每張圖表都親手繪製、而不是從函式庫直接套用的前端。
